> **ข้อเท็จจริงจาก source ที่คนแปลงเป็นสเปกต้องรู้**
> 1. **"ตีกลับ" เป็นสองจังหวะ ไม่ใช่ปุ่มเดียว** — จังหวะที่ 1 คือมาร์ครายการ: ปุ่ม **Send for Review** ในแถบเหนือตารางรายการ (`pr-item-fields.tsx:415-425`) เปิดกล่อง `Review Selected Items` แล้ว `handleBulkActionConfirm` เพียง **setValue ในฟอร์ม** (`pr-item-fields.tsx:321-344` → `use-pr-form-actions.ts:639-656`) **ไม่ยิง API** · จังหวะที่ 2 คือตีกลับทั้งใบ: ปุ่ม **Send Back** ที่แถบสรุปล่าง ซึ่งโผล่ก็ต่อเมื่อ `computePurchaseAction` คืน `"review"` คือมีอย่างน้อยหนึ่งแถวสถานะ `review` (`pr-footer-action.tsx:92, 223-234` + `workflow/pr-purchase-action.ts:24`) — `tests/pages/pr-approver.helpers.ts` (`bulkSendForReview`) ทำสองจังหวะนี้ให้แล้ว
> 2. **ขั้นปลายทางบังคับเลือก เหตุผลไม่บังคับ** — `PrActionDialog` ตั้ง `stageRequired = showStages && !selectedStage` และ **disable ปุ่มยืนยัน** จนกว่าจะเลือก (`workflow/pr-action-dialog.tsx:121, 284`) ส่วนช่องเหตุผลเป็น `Textarea` `maxLength={256}` ที่ไม่มีเงื่อนไขบังคับ placeholder เขียนว่า `Enter reason (optional)...` ตรง ๆ (`pr-action-dialog.tsx:235-243, 259-267`) · รายชื่อขั้นมาจาก `usePrPreviousStages` (`use-purchase-request.ts:303-322`) ซึ่ง enable เฉพาะใบที่มี `workflow.id` และ `workflow_current_stage` (`pr-form.tsx:64-69`) ⇒ **ตีกลับข้ามขั้นได้เท่าที่ endpoint นี้คืนมา ไม่ใช่ขั้นก่อนหน้าหนึ่งขั้นเสมอ**
> 3. **กล่องตีกลับแสดงช่องเหตุผลเฉพาะแถวที่ถูกมาร์ค** — `reviewItems` กรองเอาเฉพาะ item ที่ `current_stage_status === review` (`pr-footer-action.tsx:107-116`) ใบสิบแถวที่มาร์คสองแถวจึงเห็นช่องเหตุผลสองช่อง ไม่ใช่สิบช่อง
> 4. **ปิดกล่องแล้วค่าหาย** — `handleOpenChange` ล้างทั้ง `messages` และ `selectedStage` เมื่อปิด (`pr-action-dialog.tsx:130-136`)
> 5. **ตีกลับสำเร็จแล้วเด้งออกจากหน้า** — `handleReview` เรียก `saveDirtyEdits()` ก่อน (ค่าที่แก้ค้างในฟอร์มถูก `/save` ก่อนยิง action — `use-pr-form-actions.ts:610, 253-272`) ดึง `doc_version` สดกัน 409 (`:624`) แล้ว `onSuccess: onSuccessList(t("sentBack"))` ซึ่ง **toast `Purchase request sent back` + `navigate("/procurement/purchase-request")`** (`:187-190, 634-637`) — อย่าคาดหวังว่ายังอยู่หน้ารายละเอียด
> 6. **ส่งใหม่ก็เด้งออกเหมือนกัน** — ปุ่ม Submit โผล่เมื่อ `role === create` โดย **ไม่ดูสถานะใบ** (`pr-footer-action.tsx:89, 101`; บรรทัด 88 เป็นเงื่อนไขเดิมที่ถูกคอมเมนต์ทิ้ง) กดแล้ว `validateSubmitPr` ตรวจก่อนเปิดกล่อง (`use-pr-form-actions.ts:520-533`) ยืนยันแล้ววิ่ง `doSaveAndSubmitPr` → `/save` แล้ว `/submit` → `onSuccessList(t("submitted"))` = toast `Purchase request submitted` + กลับหน้ารายการ (`:366-390, 357`) ⇒ **`TC-PR-080708` ในสเปกที่รอ badge `in progress` บนหน้ารายละเอียดจึงขัดกับพฤติกรรมจริง** บันทึกไว้เป็นข้อเท็จจริง ไฟล์นี้ไม่เขียนเคสซ้ำ
> 7. **`role` มาจาก backend ไม่ใช่สถานะใบ** — `purchaseRequest.role` เป็นตัวตัดสินว่าปุ่มไหนโผล่ (`pr-form.tsx:80`) ใบที่ตีกลับมาถึงผู้สร้างจะได้ `role = create` ซึ่งทำให้ปุ่ม Submit กลับมาและปุ่มตัดสินของผู้อนุมัติหายไป
> 8. **ผู้สร้างเห็นตารางรายการคนละทรงกับผู้อนุมัติ** — `isCreateRole` ตัด **คอลัมน์ select (ช่องติ๊ก)** และ **คอลัมน์ Approved** ออก (`use-pr-item-table.tsx:461-482`) แต่จุดสถานะรายแถวยังโชว์ผ่าน `statusSlot` ของเซลล์คลัง (`:254-269`) ⇒ ผู้สร้าง **เห็น** ว่าแถวไหนเป็น `REVIEW` แต่เคลียร์เองไม่ได้ (ปุ่ม X ผูกกับ role `approve`/`purchase` เท่านั้น — `pr-item-cells/status-cell.tsx:39-42, 61-66`)
> 9. **แถวที่อนุมัติมาแล้วล็อกสำหรับผู้สร้าง** — `isRowLocked` ล็อกแถวที่ `_initial_stage_status` เป็น `approved`/`rejected` สำหรับทุก role ยกเว้น `purchase` (`pr-item-cells/helpers.tsx:50-87, 110-128`) ใบที่ผู้อนุมัติ approve บางแถวแล้วตีกลับที่เหลือ ผู้สร้างจึงแก้ได้เฉพาะแถวที่ถูกมาร์ค review

> - **กลุ่มที่ต้องมีใบอยู่ที่ขั้น HOD (ยังไม่ถูกตีกลับ)** — seed = `submitPRAsRequestor()`: `080801`, `080802`, `080803`, `080804`, `080805`, `080806`, `080807`, `080809`, `080810`, `080811`, `080828`

> **🚫 Blocker — เคสที่เปลี่ยนสถานะเอกสารและย้อนไม่ได้**

## TC-PR-080801 — ปุ่ม Send Back ระดับเอกสารโผล่ก็ต่อเมื่อมีแถวที่ถูกมาร์ค Review แล้ว

**Preconditions**
Login เป็น HOD (`hod@blueledgers.com`, BU = `BLAVG`); มีใบขอซื้อที่รออนุมัติอยู่ที่ขั้น HOD อย่างน้อย 1 ใบ — seed ด้วย `submitPRAsRequestor()` ใบใหม่เฉพาะเคสนี้

ขั้นที่ 2 แถบสรุปล่าง **ไม่มี**ปุ่ม "Send Back" (มีเพียงปุ่ม Approve หรือไม่มีปุ่มตัดสินเลย ขึ้นกับสถานะของแถว) · หลังขั้นที่ 3 ปุ่ม "Send Back" ปรากฏขึ้นในแถบสรุปล่าง — ปุ่มนี้ผูกกับ "มีอย่างน้อยหนึ่งแถวสถานะ review" ไม่ใช่กับสถานะของเอกสาร · ยังไม่มีการเปลี่ยนแปลงใดถูกบันทึก (ใบยังอยู่ในคิวของ HOD ถ้ารีเฟรชโดยไม่กดยืนยัน)
