# Gap Reports

เคสที่ **สเปกอัตโนมัติยังไม่ครอบ** ของโมดูลที่ *มีสเปกแล้ว* — ต่างจาก
[`../`](../) ที่เป็นแคตตาล็อกเต็มของโมดูลที่ยังไม่มีสเปกเลย

อ่านคู่กับ [`../COVERAGE.md`](../COVERAGE.md) ซึ่งบอกว่าโมดูลไหนอยู่สถานะใด

## กติกาของโฟลเดอร์นี้

- **ใช้ prefix ของสเปกเอง** (`TC-PR-…` สำหรับ `301-pr.spec.ts`) แล้วเลือกช่วง ID
  ที่ยังว่าง จึง**ไม่ต้องมีแถวของตัวเองใน** [`../../test-id-scheme.md`](../../test-id-scheme.md)
  `bun audit:tc-ids` สแกนโฟลเดอร์นี้ด้วยและจะฟ้อง `CROSS_FILE_DUPLICATE` ถ้าเลขชนกับสเปก
- **`bun audit:coverage` ไม่นับไฟล์ในนี้เป็นความครอบคลุม** โดยตั้งใจ — เอกสารที่บอกว่า
  สเปก*ไม่*ครอบอะไร ถ้านับเป็นความครอบคลุมจะให้ผลตรงข้ามกับที่มันเขียนไว้
- **เมื่อเคสใดถูกเขียนเป็นสเปกแล้ว ให้ลบออกจากไฟล์นี้** และเมื่อไฟล์ว่างให้ลบทิ้ง

## ข้อจำกัดที่รู้อยู่: หมายเลข section ไม่ตรงขนบเสมอไป

สเปกส่วนใหญ่ลงทะเบียน section ไว้แค่ `01, 03–05, 10, 20` gap report จึงจัดเคสที่ตาม
ขนบควรอยู่บล็อกอื่นเข้าบล็อกที่ใกล้เคียงที่สุดแทน ที่พบบ่อยคือ

| เคส | ขนบ | ที่อยู่จริงในไฟล์เหล่านี้ |
| --- | --- | --- |
| Export / integration ข้ามโมดูล | 30 | 01 หรือ 04 |
| หน้ารายละเอียด / deep link | 02 | 04 |
| Edge case | 90 | 01 |

ทำแบบนี้เพราะ `bun audit:tc-ids` เป็น strict — ใช้ section ที่ไม่ได้ลงทะเบียนแล้วจะ
ฟ้อง `UNKNOWN_SECTION` ทันที และการลงทะเบียน section เพิ่มโดยไม่มีเคสใช้จริงก็จะถูก
สคริปต์ sync ลบออกอยู่ดี

**ถ้าจะจัดให้ตรงขนบ** ต้องทำสองอย่างพร้อมกัน: ย้าย ID ในไฟล์ gap ไปบล็อกที่ถูก แล้ว
รันสคริปต์ที่อ่าน section จากเคสจริงเพื่ออัปเดต `test-id-scheme.md` — ยังไม่ได้ทำเพราะ
ต้องย้าย ID หลายสิบตัวข้ามหลายไฟล์ และเมื่อเคสเหล่านี้ถูกแปลงเป็นสเปกจริง เลขจะถูกจัด
ใหม่อยู่แล้ว
