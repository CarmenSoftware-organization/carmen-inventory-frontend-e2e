>   - **ปุ่ม Back กลับหน้า list เสมอ ไม่ใช่ถอย history** (`77002718`) และคืนสถานะ filter/sort/tab ของ list ที่จากมา (`ed073757`)

>   - ฟอร์มถูกยุบเข้า `useEntityForm` (`58bc29a8`) — dirty guard มี **สองชั้น**: `useDiscardConfirm` (ปุ่ม Cancel/Back ในฟอร์ม) และ `useNavigationGuard` (ลิงก์นอกฟอร์ม เช่น เมนู sidebar, `dfbbfc9a`) ทั้งคู่เด้ง `DiscardDialog` variant `warning` ที่มีปุ่ม **"Keep editing" / "Discard"** หัวข้อ **"Discard changes?"**

>   - ฟอร์มบีบความกว้างเหลือ `max-w-4xl` (`3ed56077`) — ไม่เต็มจอแบบ matrix เดิม
> - **เพิ่ม 16 เคสใหม่** ครอบพฤติกรรมที่ไม่มีใครครอบ: sort/pagination/ล้างคำค้นที่ sync กับ URL (01), ตัวนับ section + หน้า not-found + ปุ่ม Back โหมด view (02), select-all รายแถว + Cancel ที่ยังไม่ dirty (03), navigation guard ข้ามหน้า + สถานะ Saving (04), Delete หายในโหมด edit (05), permission-denied ของเมนู sidebar และของปุ่มลบในแถว (10), scroll/โฟกัสช่องที่ผิด (20), แถว Module access + ตัวนับหมวด/indeterminate + ลำดับหมวด + Print (40)
>
> **Blocker ที่คนแปลงเป็น spec ต้องรู้**
>
> 1. **โมดูลนี้แก้สิทธิ์จริงในระบบ** — role ที่เห็นในหน้านี้คือ role เดียวกับที่ผูกกับบัญชีทดสอบใน `tests/test-users.ts` เคสที่ **แก้ / ถอนสิทธิ์ / ลบ** ห้ามชี้ไปที่ role ของบัญชีเหล่านั้นเด็ดขาด (requestor / hod / purchase / fc / gm / owner / storemanager / budget / admin @blueledgers.com) เพราะสิทธิ์ที่ถูกแก้จะทำให้ `auth.setup.ts` และสเปกอื่น **ทั้งชุด** ล้มในรันถัดไป และกู้คืนไม่ได้จากฝั่งเทส — ทุกเคสของบล็อก 04/05 ต้อง **สร้าง role ใหม่ของตัวเองก่อน** แล้วแก้/ลบเฉพาะตัวนั้น
> 2. **ไม่มีทางแยกโหมด view/edit ด้วย URL** — `/system-admin/role/:id` เปิดมาเป็น view เสมอ (`useEntityForm` ตั้ง `mode = entity ? "view" : "add"`) ต้องกดปุ่ม Edit ก่อนทุกครั้ง
> 3. **ต้องมี `doc_version`** — `role-form.tsx` ส่ง `doc_version` ของระเบียนที่โหลดมาไปกับ PUT (optimistic concurrency) เปิดสองแท็บแล้วเซฟทับกันจะได้ error จาก backend ไม่ใช่ last-write-wins
> 4. **payload ของ update เป็น diff ไม่ใช่ค่าเต็ม** — `permissions: { add, remove }` คำนวณเทียบกับชุดสิทธิ์ตอนโหลด การ assert ที่ระดับ network ต้องดูสองอาเรย์นี้ ไม่ใช่รายการสิทธิ์ทั้งก้อน
> 5. **Print ใช้ `window.print()` ผ่าน iframe ซ่อน** (`lib/print-html.ts`) — เป็น native print dialog ที่ Playwright ขับไม่ได้ เคส `TC-ROLE-400007` จึง assert ได้แค่ว่าปุ่มมีจริงและกดแล้วไม่พาออกจากหน้า/ไม่เปิดแท็บใหม่ ถ้าอยากตรวจเนื้อเอกสารต้อง stub `window.print` ด้วย `page.addInitScript` แล้วอ่าน `srcdoc` ของ iframe ก่อนถูก cleanup
> 6. **เคสบล็อก 10 ต้องใช้บัญชีที่ไม่ใช่ admin ของ BU และไม่มีสิทธิ์ `system_configuration.view`** — leaf `/system-admin/role` ใน `constant/module-list.ts` ใช้ permission ตัวนี้ (ไม่ใช่ `system_admin.role` ซึ่งเป็น **licenseFeature** คนละแกน) และ `useCan()` ให้ admin ของ BU ผ่านทุกอย่าง ต้องยืนยันกับข้อมูลจริงก่อนว่าบัญชีไหนใน `tests/test-users.ts` เข้าเงื่อนไข — ถ้าไม่มีเลย เคส 10 ต้องรอบัญชีใหม่
> 7. **`constant/permissions.ts` ไม่มี namespace `system_admin`** — สิทธิ์ที่ใช้คุมหน้านี้จึงเป็น `system_configuration.view/update` ส่วน catalog สิทธิ์ที่โชว์ใน picker มาจาก **API `GET /permissions?perpage=-1` ตอนรันไทม์** ไม่ใช่จากไฟล์นี้ จำนวน/ชื่อ resource จึงขึ้นกับข้อมูลใน BU ที่ทดสอบ ห้าม hardcode จำนวนสิทธิ์รวม
> 8. **`useRole` ใช้ `CACHE_STATIC` (staleTime 30 นาที)** — หลัง create/update/delete มี `invalidateKeys` ให้แล้ว แต่ถ้าเทสสร้าง role ผ่าน API ตรง ๆ แล้วมาเปิดหน้า list ทันที อาจยังเห็นข้อมูลเก่าจนกว่าจะ reload
